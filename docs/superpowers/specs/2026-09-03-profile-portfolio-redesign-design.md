# ShapArt Profile Portfolio Redesign — Design Spec

## Goal

Turn the profile repository into a distinctive engineering portfolio: visually authored, alive, and credible to both technical reviewers and recruiters, without the common "generated GitHub profile" look.

## Direction

Use an **Engineering Editorial + Living Profile** system.

The visual language should feel closer to a technical magazine, research dossier, or product case-study index than to a terminal theme or badge wall. The profile should remain readable in GitHub's native renderer and work in both light and dark surrounding UI.

## Reference principles

The redesign borrows mechanics rather than copying aesthetics:

- from minimal/descriptive profiles: short human introduction and low decoration density;
- from Simon Willison-style self-updating profiles: current releases and activity generated by GitHub Actions;
- from strong project-card profiles: projects are scannable as visual objects, but cards are locally owned SVG assets rather than remote stats widgets;
- from the curated `awesome-github-profile-readme` catalog: use motion/dynamic content only where it communicates real activity.

## Anti-patterns to avoid

Do not use:

- fake terminal UI, `whoami`, command prompts, fake cursors;
- typing/deleting SVG copy;
- trophy walls, profile-view counters, streak rankings or A+ scores;
- giant screenshots of application UIs in the main profile;
- more than a small handful of badges;
- anime/GIF decoration, random quotes, Spotify widgets;
- a giant hero taking most of the first viewport;
- wording such as "passionate developer", "always learning", or generic AI-generated career copy.

## Information architecture

The README should be ordered as follows:

1. **Masthead** — compact authored SVG, around 160–210 px tall.
2. **Identity / introduction** — name, direction, short human description, target roles, links.
3. **Proof line** — three concrete facts rendered as plain text, not badges:
   - OpenText bulk work: hours → about 10 minutes for covered scenarios;
   - Alfa CTF 2026: #45;
   - 3+ years of professional systems / automation experience before the current role.
4. **Selected work** — four visual project cards in a 2×2 HTML table:
   - OpenText Toolkit / Matrix Cleaner;
   - TESSA Matrix Studio;
   - EyeGate-L;
   - SH4PART VPN.
5. **Recently shipped** — generated block showing current releases/updates from selected public repositories.
6. **Experience** — Cherkizovo first, NAOS second; concise and outcome-driven.
7. **Security / stack** — grouped compact text, not an icon wall.
8. **Education / evidence** — BMSTU, VK Education, Digital Department, Alfa CTF, with certificates collapsed or linked.
9. **Activity** — existing contribution snake at the bottom only.
10. **Russian summary** — short, human, collapsed or low on the page.

## Visual system

### Masthead

Create `assets/masthead.svg`.

- Aspect ratio close to 1200×220.
- Editorial geometry, not UI chrome.
- Off-black / graphite base with restrained warm-white and one cool accent.
- Content: `SHAPART / ARTYOM SHAPOVALOV`, `security automation · systems · backend`, and a small issue/date-like index such as `PROFILE / 2026`.
- Use abstract routing/matrix/grid geometry as texture.
- No terminal window, fake controls, fake CLI, neon hacker imagery or portrait.

### Project covers

Create four local SVG covers under `assets/projects/`.

All covers share a system: same dimensions, type hierarchy and margins; each has its own geometric metaphor.

- `matrix-cleaner.svg`: matrix/routing rows, one bounded change path, preview/verify motif.
- `tessa-matrix-studio.svg`: spreadsheet cells transitioning into structured route nodes; no UI screenshot.
- `eyegate-l.svg`: camera/iris geometry meeting edge/access-control boundary.
- `sh4part-vpn.svg`: small topology/tunnel nodes, provisioning path, restrained network diagram language.

No project cover may contain fake metrics or invented claims.

## Dynamic "Recently shipped" block

Create a local script and GitHub Action that update only the content between stable README markers:

```html
<!-- RECENTLY-SHIPPED:START -->
<!-- RECENTLY-SHIPPED:END -->
```

Source repositories:

- `ShapArt/Matrtix-Cleaner`
- `ShapArt/tessa-matrix-studio`
- `ShapArt/eyegate-l-luckfox-scud`
- `ShapArt/vpn-bot-stars-hiddify`

Rules:

- Prefer the latest non-draft, non-prerelease release when one exists.
- If a repository has no release, use the latest default-branch commit.
- Show at most four items, newest first.
- Each item contains repository/project name, release/tag or concise commit title, and date.
- Do not copy long release bodies.
- Script must preserve the rest of README byte-for-byte outside marker content.
- Workflow runs daily and manually; it commits only when README content actually changes.
- Use GitHub's built-in token; no external service or secret is required.

## Copy tone

The voice should be compact, calm and specific.

Preferred:

> I work on the awkward boundary between enterprise systems, security controls and manual operations.

Avoid:

> Passionate cybersecurity enthusiast building innovative solutions with cutting-edge technologies.

Projects should lead with what problem they solve and what engineering constraint made them interesting.

## Privacy / confidentiality

Public copy must not expose private internal URLs, employee names, credentials, internal matrix contents, customer data or sensitive business configuration. Enterprise work can describe architecture, workflow shape and quantified time savings only at the already-approved public level.

## Existing artifacts

Keep and link:

- `PORTFOLIO.md`
- `RESUME.md`
- `CERTIFICATES.md`
- `HH_RU_PROFILE.txt`
- existing contribution snake workflow/output

The old `assets/profile-hero.svg` can remain in repository history/assets but must no longer be referenced from README.

## Validation

Before calling the redesign complete:

1. README contains no old hero and no product screenshot.
2. Four project SVGs render from local repository paths.
3. README has exactly one pair of `RECENTLY-SHIPPED` markers.
4. Dynamic updater can run twice without creating a second change (idempotent).
5. Existing markdown link CI succeeds.
6. New workflow completes successfully with `contents: write` only.
7. No generated section contains private repository data or inaccessible links.
